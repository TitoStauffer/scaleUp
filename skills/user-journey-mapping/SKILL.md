# User Journey Mapping

## 1. Objetivo

Mapear a experiência de um usuário ao longo de uma jornada completa para compreender:

- o que ele está tentando alcançar;
- quais etapas percorre;
- quais ações realiza;
- quais pontos de contato utiliza;
- o que pensa e sente;
- onde encontra dificuldades;
- quais necessidades possui;
- onde existem oportunidades de melhoria.

Esta Skill deve transformar uma experiência fragmentada em uma visão sistêmica.

A pergunta central é:

> "Como é a experiência do usuário do início ao fim para alcançar determinado objetivo?"

---

# 2. Princípios Fundamentais

## 2.1 Mapear a experiência, não apenas as telas

Uma jornada não é uma sequência de telas.

Ela pode envolver:

- produto;
- atendimento;
- e-mail;
- WhatsApp;
- telefone;
- documentação;
- sistemas externos;
- processos manuais;
- outras pessoas;
- ambientes físicos.

Exemplo:

```text
Usuário identifica necessidade
        ↓
Pesquisa solução
        ↓
Entra no produto
        ↓
Realiza cadastro
        ↓
Recebe comunicação
        ↓
Executa tarefa
        ↓
Busca suporte
        ↓
Conclui objetivo
```

A jornada deve considerar toda a experiência relevante.

---

# 3. Quando Usar

Use esta Skill quando for necessário:

- compreender uma experiência ponta a ponta;
- mapear processos de usuário;
- descobrir pontos de fricção;
- analisar onboarding;
- analisar checkout;
- analisar cadastro;
- analisar compra;
- analisar suporte;
- analisar processos complexos;
- identificar oportunidades de UX;
- entender dependências externas;
- alinhar equipes sobre uma experiência;
- investigar abandono;
- priorizar problemas de experiência.

---

# 4. Quando NÃO Usar

Não utilizar esta Skill quando:

- a tarefa é apenas criar uma tela;
- o problema está limitado a um componente;
- o fluxo é trivial e já conhecido;
- não existe uma jornada relevante;
- o objetivo é somente definir identidade visual.

Nesses casos, utilizar uma Skill mais específica.

---

# 5. Definir o Escopo da Jornada

Antes de criar o mapa, definir:

```text
Persona:
[quem]

Objetivo:
[o que deseja alcançar]

Contexto:
[em qual situação]

Início:
[onde a jornada começa]

Fim:
[onde a jornada termina]
```

Exemplo:

```text
Persona:
Novo cliente

Objetivo:
Realizar a primeira compra

Contexto:
Está avaliando o produto pela primeira vez

Início:
Descoberta do produto

Fim:
Compra concluída
```

---

# 6. Jornada Atual x Jornada Desejada

Diferenciar:

### Jornada Atual

Como a experiência funciona hoje.

### Jornada Desejada

Como a experiência deveria funcionar.

Nunca substituir a jornada atual pela desejada sem deixar essa distinção explícita.

Fluxo:

```text
Jornada Atual
      ↓
Problemas
      ↓
Oportunidades
      ↓
Jornada Desejada
```

---

# 7. Etapas da Jornada

Dividir a experiência em etapas significativas.

Exemplo:

```text
1. Descoberta
2. Avaliação
3. Cadastro
4. Configuração
5. Primeiro uso
6. Uso recorrente
7. Suporte
8. Retenção
```

O número de etapas deve ser proporcional à complexidade.

Evitar criar dezenas de etapas artificiais.

---

# 8. Objetivo de Cada Etapa

Cada etapa deve responder:

> "O que o usuário está tentando alcançar aqui?"

Exemplo:

```text
Etapa:
Cadastro

Objetivo:
Criar uma conta e começar a utilizar o produto.
```

Não confundir objetivo do usuário com objetivo do negócio.

---

# 9. Ações do Usuário

Registrar o que o usuário efetivamente faz.

Exemplos:

- pesquisa;
- compara;
- clica;
- preenche;
- envia;
- confirma;
- espera;
- consulta documentação;
- conversa com suporte;
- abandona;
- retorna;
- utiliza uma alternativa.

Preferir comportamentos observáveis.

---

# 10. Pensamentos

Quando houver evidências, registrar o que o usuário provavelmente está pensando.

Exemplo:

```text
"Será que meus dados foram enviados?"

"Quanto tempo isso vai demorar?"

"Posso confiar nesse resultado?"
```

Diferenciar:

### Evidência

Usuário declarou explicitamente esse pensamento.

### Inferência

O pensamento foi inferido a partir de comportamento.

Não apresentar inferências como citações ou fatos.

---

# 11. Emoções

Mapear emoções relevantes ao longo da jornada.

Exemplos:

- curiosidade;
- confiança;
- dúvida;
- ansiedade;
- frustração;
- alívio;
- satisfação;
- insegurança.

Não transformar emoções em decoração.

O objetivo é identificar como a experiência influencia percepção e comportamento.

---

# 12. Touchpoints

Identificar todos os pontos de contato relevantes.

Exemplos:

```text
Website
Aplicativo
Sistema web
E-mail
WhatsApp
Telefone
Atendimento
Documentação
Notificação
Equipe comercial
Sistema externo
```

Um touchpoint pode estar fora do produto principal.

---

# 13. Canais

Registrar onde a interação acontece.

Exemplo:

```text
Etapa:
Recuperação de conta

Canais:
- Web
- E-mail
- WhatsApp
```

Identificar inconsistências entre canais.

---

# 14. Dores

Registrar problemas encontrados em cada etapa.

Exemplo:

```text
Etapa:
Cadastro

Dor:
Usuário não entende quais documentos precisa enviar.
```

Classificar quando útil:

- cognitiva;
- operacional;
- técnica;
- informacional;
- emocional;
- organizacional.

---

# 15. Barreiras

Diferenciar dor de barreira.

### Dor

Experiência negativa.

### Barreira

Fator que impede ou dificulta o avanço.

Exemplo:

```text
Dor:
Usuário fica inseguro durante o pagamento.

Barreira:
Não existe informação clara sobre segurança.
```

---

# 16. Necessidades

Identificar o que o usuário precisa para avançar.

Exemplo:

```text
Etapa:
Pagamento

Necessidade:
Ter confiança de que a transação será processada corretamente.
```

Não converter imediatamente a necessidade em solução.

---

# 17. Oportunidades

Depois de identificar problemas, formular oportunidades.

Formato:

```text
Como poderíamos...

[resolver ou reduzir determinado problema]
```

Exemplo:

```text
Como poderíamos aumentar a confiança do usuário
durante o pagamento?
```

Evitar formular oportunidades como soluções específicas.

Ruim:

> "Como poderíamos adicionar um modal?"

Melhor:

> "Como poderíamos deixar o estado da transação mais claro?"

---

# 18. Moments That Matter

Identificar momentos críticos da jornada.

Nem todas as etapas possuem o mesmo peso.

Exemplos:

- primeiro contato;
- primeiro sucesso;
- pagamento;
- erro;
- espera;
- confirmação;
- cancelamento;
- suporte;
- recuperação.

Classificar impacto quando necessário.

```text
Baixo
Médio
Alto
Crítico
```

---

# 19. Pain Points

Pain points são pontos da jornada onde existe fricção significativa.

Avaliar:

```text
Frequência
+
Impacto
+
Severidade
+
Esforço
```

Exemplo:

```text
Pain Point:
Usuários abandonam o cadastro ao descobrir que precisam
de um documento não informado anteriormente.

Frequência:
Alta

Impacto:
Alto

Severidade:
Alta
```

---

# 20. Fricção

Fricção pode surgir de:

### Cognitiva

Usuário precisa pensar demais.

### Operacional

Usuário precisa realizar ações desnecessárias.

### Informacional

Informações importantes não estão disponíveis.

### Técnica

Sistema apresenta falhas ou lentidão.

### Emocional

Usuário sente insegurança, ansiedade ou frustração.

### Contextual

A experiência não se adapta ao ambiente de uso.

---

# 21. Dependências Externas

Mapear dependências que impactam a jornada.

Exemplos:

- banco;
- gateway;
- parceiro;
- fornecedor;
- sistema governamental;
- atendimento humano;
- e-mail;
- autenticação;
- dispositivo.

Essas dependências podem criar pontos de fricção mesmo quando a interface principal está correta.

---

# 22. Estados da Jornada

Não mapear apenas o caminho ideal.

Considerar:

```text
Happy Path
     ↓
Erro
     ↓
Recuperação
     ↓
Sucesso
```

Também considerar:

- abandono;
- retorno;
- timeout;
- indisponibilidade;
- dados inválidos;
- usuário sem permissão;
- usuário sem informação;
- ação duplicada.

---

# 23. Happy Path

Representar o fluxo ideal:

```text
Início
 ↓
Ação
 ↓
Resposta
 ↓
Próxima ação
 ↓
Conclusão
```

O happy path não deve ser tratado como a jornada completa.

---

# 24. Edge Cases

Identificar situações que desviam do fluxo principal.

Exemplos:

- usuário perdeu acesso;
- informação inválida;
- operação duplicada;
- serviço externo indisponível;
- usuário interrompe processo;
- usuário retorna depois de muito tempo;
- permissão insuficiente.

Esses casos frequentemente revelam grandes oportunidades de UX.

---

# 25. Jornada Multicanal

Quando a jornada envolver vários canais, preservar a continuidade.

Exemplo:

```text
Website
   ↓
E-mail
   ↓
WhatsApp
   ↓
Atendimento
   ↓
Website
```

Investigar:

- perda de contexto;
- repetição de informações;
- inconsistência de mensagens;
- informações divergentes;
- falta de continuidade.

---

# 26. Jornada Emocional

Quando relevante, representar a evolução emocional.

Exemplo:

```text
Curiosidade
   ↓
Confiança
   ↓
Dúvida
   ↓
Frustração
   ↓
Alívio
   ↓
Satisfação
```

Utilizar somente quando houver evidência ou inferência razoável.

---

# 27. Jornada e Métricas

Quando existirem métricas, associá-las às etapas.

Exemplo:

```text
Cadastro
↓
Conversão: 82%

Confirmação
↓
Abandono: 18%

Primeiro uso
↓
Ativação: 64%
```

Isso conecta experiência qualitativa e comportamento quantitativo.

---

# 28. Journey Mapping e UX Research

A jornada deve utilizar evidências do UX Research.

Fluxo:

```text
UX Research
    ↓
Evidências
    ↓
Padrões
    ↓
Journey Map
    ↓
Pain Points
    ↓
Oportunidades
```

Não criar uma jornada fictícia apenas para preencher um template.

---

# 29. Journey Mapping e Personas

Sempre que uma persona estiver disponível, indicar:

```text
Persona:
[persona]
```

A jornada representa a experiência daquela persona naquele contexto.

Diferentes personas podem possuir jornadas diferentes.

---

# 30. Jornada e Product Management

O Product Manager pode definir:

- objetivo do produto;
- resultado esperado;
- problema de negócio;
- restrições.

O Journey Map ajuda a compreender:

- onde o usuário enfrenta problemas;
- onde existe fricção;
- quais momentos importam;
- quais oportunidades existem.

Fluxo:

```text
Product Manager
       ↓
Objetivo
       ↓
Persona
       ↓
Journey Map
       ↓
Pain Points
       ↓
Oportunidades
       ↓
Requirements / Backlog
```

---

# 31. Jornada Atual

Quando documentar a jornada atual:

Não melhorar artificialmente o processo.

Registrar como ele realmente funciona.

Exemplo:

```text
Usuário envia documento
↓
Sistema demora
↓
Usuário não recebe feedback
↓
Usuário entra em contato com suporte
↓
Suporte confirma manualmente
↓
Usuário continua
```

Essa realidade pode parecer "feia", mas é justamente o que torna o mapa útil.

---

# 32. Jornada Desejada

Somente depois de compreender a jornada atual, desenhar a desejada.

Exemplo:

```text
Usuário envia documento
↓
Sistema confirma recebimento
↓
Processamento
↓
Atualização de status
↓
Conclusão
```

Toda mudança deve estar relacionada a um problema ou oportunidade identificada.

---

# 33. Priorizar Oportunidades

Quando existirem muitas oportunidades, priorizar usando:

```text
Impacto no usuário
+
Frequência
+
Severidade
+
Valor para o negócio
+
Esforço
```

Evitar tratar todos os pain points como igualmente importantes.

---

# 35. Nível de Confiança

Classificar elementos importantes do mapa.

### Alta

Baseado em evidências sólidas.

### Média

Baseado em evidências parciais.

### Baixa

Baseado em hipótese ou inferência.

Exemplo:

```text
Dor:
Usuário abandona o fluxo por falta de informação.

Confiança:
Média

Evidência:
Analytics + entrevistas limitadas.
```

---

# 36. Quando Não Houver Evidência

Nunca inventar:

- pensamentos;
- emoções;
- comportamentos;
- touchpoints;
- dores;
- necessidades.

Utilizar:

```text
Desconhecido
```

ou:

```text
Hipótese
```

Exemplo:

```text
Emoção:
Hipótese — insegurança

Necessário:
Validar em pesquisa.
```

---

# 37. Anti-Patterns

Evitar:

### Happy Path Only

Mapear apenas o caminho ideal.

### Screen Mapping

Confundir jornada com sequência de telas.

### Fictional Journey

Criar comportamentos sem evidência.

### Solution Mapping

Transformar cada dor diretamente em uma solução.

### Journey Theater

Criar um mapa bonito que não influencia decisões.

### Excessive Detail

Adicionar centenas de informações irrelevantes.

### No Prioritization

Tratar todos os problemas como igualmente importantes.

### Business-Centric Journey

Descrever somente o que a empresa quer que aconteça.

### Static Journey

Nunca atualizar o mapa após novas evidências.

---

# 38. Critérios de Qualidade

Um bom Journey Map deve:

- ter persona ou segmento definido;
- possuir objetivo claro;
- possuir início e fim;
- representar a experiência real;
- mostrar etapas relevantes;
- registrar ações;
- identificar touchpoints;
- identificar dores;
- identificar necessidades;
- destacar momentos críticos;
- considerar estados alternativos;
- distinguir fatos de hipóteses;
- apontar oportunidades;
- permitir priorização;
- orientar decisões.

---

# 39. Regra de Ouro

> **Mapeie a jornada como ela realmente acontece, não como você gostaria que ela acontecesse.**

Primeiro compreender.

Depois identificar problemas.

Depois descobrir oportunidades.

Somente então projetar uma nova experiência.
