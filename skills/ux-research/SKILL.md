# UX Research

## 1. Objetivo

Investigar e compreender profundamente os usuários, seus objetivos, comportamentos, necessidades, dores, motivações e contexto de uso para orientar decisões de produto e UX baseadas em evidências.

Esta Skill existe para responder:

> "O que sabemos sobre o usuário e como sabemos disso?"

Ela NÃO existe para criar interfaces diretamente.

O foco é reduzir incerteza antes que decisões de UX, UI ou produto sejam tomadas.

---

# 2. Princípios Fundamentais

## 2.1 Pesquisar antes de solucionar

Não assumir que a primeira solução imaginada é a correta.

Fluxo preferencial:

Problema
↓
Investigação
↓
Evidências
↓
Padrões
↓
Insights
↓
Hipóteses
↓
Oportunidades
↓
Solução

Evitar:

Problema
↓
Opinião
↓
Interface

---

## 2.2 Separar fato, evidência, hipótese e opinião

Nunca tratar todos os tipos de informação como equivalentes.

### Fato

Algo conhecido e verificável.

Exemplo:

> "37% dos usuários abandonam o formulário na etapa 3."

### Evidência

Informação observada ou coletada que sustenta uma conclusão.

Exemplo:

> "Em 8 entrevistas, 6 usuários demonstraram dificuldade para encontrar a opção de recuperação."

### Insight

Interpretação relevante derivada de múltiplas evidências.

Exemplo:

> "Usuários não reconhecem a recuperação de conta como parte do fluxo de login."

### Hipótese

Explicação ou suposição ainda não comprovada.

Exemplo:

> "O abandono pode estar relacionado à falta de confiança no processo."

### Opinião

Preferência ou julgamento sem evidência suficiente.

Exemplo:

> "Acho que o botão deveria ficar no topo."

Não apresentar opinião como evidência.

# 3. Quando Usar

Use esta Skill quando houver necessidade de:

- compreender usuários;
- investigar problemas de UX;
- entender comportamentos;
- descobrir necessidades;
- investigar dores e frustrações;
- estruturar entrevistas;
- analisar feedback de usuários;
- analisar tickets de suporte;
- analisar reviews;
- interpretar pesquisas existentes;
- identificar padrões comportamentais;
- validar hipóteses;
- descobrir oportunidades;
- preparar testes de usabilidade;
- entender contexto de uso;
- investigar abandono ou conversão;
- entender por que uma funcionalidade não está sendo utilizada.

---

# 4. Quando NÃO Usar

Não usar esta Skill como primeira etapa quando:

- o problema já está suficientemente compreendido;
- existe evidência sólida disponível;
- a tarefa é puramente visual;
- a tarefa é apenas implementar uma interface;
- o usuário pediu somente uma especificação visual;
- o objetivo é apenas corrigir um bug visual;
- uma decisão já foi validada anteriormente.

Nesses casos, utilizar a Skill especializada apropriada.

---

# 5. Tipos de Pesquisa

Selecionar o método de pesquisa de acordo com a pergunta que precisa ser respondida.

## 5.1 Pesquisa qualitativa

Indicada para compreender:

- por quê;
- como;
- motivações;
- percepções;
- dificuldades;
- expectativas;
- contexto;
- comportamentos.

Exemplos:

- entrevistas;
- observação;
- testes de usabilidade;
- análise de sessões;
- estudos contextuais.

---

## 5.2 Pesquisa quantitativa

Indicada para compreender:

- quanto;
- frequência;
- proporção;
- distribuição;
- tendências;
- correlações;
- magnitude do problema.

Exemplos:

- analytics;
- pesquisas estruturadas;
- métricas de produto;
- questionários;
- funis;
- dados comportamentais.

---

## 5.3 Pesquisa exploratória

Usada quando o problema ainda é pouco conhecido.

Objetivo:

> descobrir o que está acontecendo.

Priorizar perguntas abertas e coleta ampla de evidências.

---

## 5.4 Pesquisa avaliativa

Usada quando já existe uma solução ou protótipo.

Objetivo:

> descobrir se a solução funciona para o usuário.

Exemplos:

- testes de usabilidade;
- avaliação heurística;
- testes comparativos;
- análise de protótipos.

---

# 6. Formular a Pergunta de Pesquisa

Antes de escolher um método, definir claramente a pergunta.

Uma boa pergunta deve reduzir uma incerteza relevante.

### Exemplos

Ruim:

> "Os usuários gostam da tela?"

Melhor:

> "Quais partes do processo de checkout geram maior dificuldade para usuários iniciantes?"

Ruim:

> "Devemos colocar um botão maior?"

Melhor:

> "Por que usuários não encontram a ação de finalizar o pedido?"

Priorizar perguntas sobre comportamento e problema antes de perguntas sobre solução.

---

# 7. Definir Objetivo da Pesquisa

Toda pesquisa deve possuir um objetivo explícito.

Formato recomendado:

```text
Objetivo:
Entender [comportamento/problema/contexto]
de [usuário/persona]
durante [situação/fluxo]
para descobrir [incerteza/oportunidade].
```

Exemplo:

```text
Objetivo:
Entender por que novos usuários abandonam o cadastro
durante a etapa de confirmação
para identificar barreiras de confiança e usabilidade.
```

---

# 8. Definir Público

Determinar quem precisa ser investigado.

Considerar:

- perfil;
- experiência;
- frequência de uso;
- contexto;
- objetivo;
- comportamento;
- estágio no ciclo de vida;
- características relevantes para o problema.

Não assumir que todos os usuários possuem as mesmas necessidades.

Quando necessário, segmentar usuários.

Exemplo:

```text
Segmento A
Novos usuários

Segmento B
Usuários recorrentes

Segmento C
Usuários que abandonaram o fluxo
```

---

# 9. Roteiro de Entrevista

Quando entrevistas forem apropriadas, estruturar perguntas abertas.

Priorizar perguntas sobre experiências reais.

Preferir:

- "Conte sobre a última vez que você tentou fazer isso."
- "O que você esperava que acontecesse?"
- "O que você fez quando isso aconteceu?"
- "O que foi mais difícil?"
- "Como você resolveu?"

Evitar:

- "Você gostaria de um botão para fazer isso?"
- "Você acha essa tela bonita?"
- "Você usaria essa funcionalidade?"

Perguntas que sugerem a resposta podem produzir evidências enviesadas.

---

# 10. Entrevistas: Estrutura Recomendada

Uma entrevista pode seguir:

1. Contexto
2. Perfil e experiência
3. Comportamento atual
4. Experiência recente
5. Problemas e dificuldades
6. Motivações
7. Alternativas utilizadas
8. Expectativas
9. Encerramento

Sempre que possível, pedir exemplos concretos.

---

# 11. Investigar Comportamento Real

Dar maior peso ao comportamento observado do que a declarações hipotéticas.

Prioridade:

```text
Comportamento observado
        ↓
Experiência relatada
        ↓
Intenção declarada
```

Exemplo:

Um usuário pode afirmar:

> "Eu usaria essa funcionalidade."

Mas nunca ter utilizado uma funcionalidade semelhante.

Essa declaração deve ser tratada como intenção, não como comportamento comprovado.

---

# 12. Análise de Dados Qualitativos

Após coletar informações:

- organizar evidências;
- identificar padrões;
- agrupar comportamentos semelhantes;
- identificar problemas recorrentes;
- identificar exceções;
- identificar necessidades;
- formular insights;
- registrar hipóteses.

Evitar transformar uma única ocorrência em regra geral.

---

# 13. Affinity Mapping

Quando houver grande volume de informações, agrupar observações por temas.

Exemplo:

```text
Observações
    ↓
Agrupamento
    ↓
Temas
    ↓
Padrões
    ↓
Insights
```

Possíveis grupos:

- dificuldade de navegação;
- falta de confiança;
- excesso de informações;
- problemas de entendimento;
- problemas de desempenho;
- necessidade de confirmação;
- dificuldades técnicas.

---

# 14. Transformar Evidência em Insight

Um insight deve explicar algo importante sobre o comportamento do usuário.

Estrutura:

```text
Evidência
+
Contexto
+
Interpretação
=
Insight
```

Exemplo:

```text
Evidência:
Usuários consultam repetidamente a documentação antes de concluir o cadastro.

Contexto:
A consulta ocorre principalmente na etapa de confirmação.

Insight:
A etapa de confirmação não fornece confiança suficiente para que usuários concluam o processo sem buscar validação externa.
```

---

# 15. Dores, Necessidades e Motivações

Diferenciar:

**Dor**

Problema ou frustração enfrentada pelo usuário.

**Necessidade**

Algo que o usuário precisa para atingir seu objetivo.

**Motivação**

Razão pela qual o usuário deseja realizar determinada ação.

Exemplo:

```text
Objetivo:
Enviar uma nota fiscal.

Dor:
Usuário não sabe se o arquivo foi enviado corretamente.

Necessidade:
Ter confirmação clara do estado do envio.

Motivação:
Garantir que a obrigação foi concluída.
```

---

# 16. Contexto de Uso

Sempre que relevante, investigar:

- onde o usuário está;
- quando utiliza o produto;
- dispositivo;
- frequência;
- pressão de tempo;
- ambiente;
- interrupções;
- experiência técnica;
- dependências;
- ferramentas alternativas.

A mesma interface pode funcionar bem em um contexto e mal em outro.

---

# 17. Análise de Feedback

Ao analisar feedback:

Não tratar toda reclamação como requisito.

Classificar:

```text
Feedback
   ↓
Problema relatado
   ↓
Contexto
   ↓
Frequência
   ↓
Impacto
   ↓
Necessidade
   ↓
Oportunidade
```

Exemplo:

Feedback:

> "Preciso de um botão azul aqui."

Não transformar diretamente em requisito.

Investigar:

> Qual problema o usuário está tentando resolver?

---

# 18. Triangulação

Quando possível, combinar diferentes fontes.

Exemplo:

```text
Entrevistas
     +
Analytics
     +
Tickets
     +
Testes de usabilidade
     ↓
Maior confiança no insight
```

Quando diferentes fontes apontam para o mesmo problema, aumentar a confiança na conclusão.

---

# 19. Nível de Confiança

Classificar conclusões conforme a força das evidências.

**Alta confiança**

Múltiplas fontes independentes sustentam a conclusão.

**Média confiança**

Existem evidências relevantes, mas ainda existem lacunas.

**Baixa confiança**

A conclusão depende principalmente de hipóteses ou poucas observações.

Exemplo:

```text
Insight:
Usuários têm dificuldade para encontrar o histórico.

Confiança:
Média

Evidências:
- 4 entrevistas
- 2 tickets
- ausência de dados quantitativos
```

---

# 20. Evitar Viés

Durante a pesquisa, considerar possíveis vieses:

- confirmação;
- seleção;
- memória;
- resposta socialmente desejável;
- pergunta direcionada;
- amostra enviesada;
- interpretação prematura;
- excesso de confiança.

Não buscar apenas evidências que confirmem a hipótese inicial.

Também procurar evidências que possam refutá-la.

Quando o projeto possuir histórico de pesquisas, registrar:

```text

├── Público
├── Método
├── Evidências
```

Isso evita repetir pesquisas e perder conhecimento histórico.

# 23. Quando Não Houver Dados

Nunca inventar resultados de pesquisa.

Se não existirem dados suficientes:

```text
Não há evidências suficientes para concluir X.

Hipótese atual:
Y

Para aumentar a confiança, recomenda-se:
Z
```

Distinguir explicitamente:

- Conhecido
- Hipótese
- Desconhecido

# 24. Relação com Product Management

Esta Skill deve trabalhar em conjunto com o Product Manager.

**Product Manager**

Define:

- problema de negócio;
- objetivo;
- oportunidade;
- resultado esperado;
- restrições.

**UX Research**

Investiga:

- usuário;
- comportamento;
- contexto;
- necessidades;
- dores;
- evidências;
- oportunidades de experiência.

Fluxo:

```text
Product Manager
      ↓
Problema / Objetivo
      ↓
UX Research
      ↓
Evidências
      ↓
Insights
      ↓
Product Manager + UX
      ↓
Decisão de produto
```

# 26. Critérios de Qualidade

Uma pesquisa de UX bem executada deve:

- possuir objetivo claro;
- responder uma pergunta relevante;
- investigar usuários adequados;
- utilizar método apropriado;
- separar evidências de interpretações;
- identificar padrões;
- registrar limitações;
- explicitar nível de confiança;
- evitar conclusões baseadas em evidência insuficiente;
- gerar insights acionáveis;
- reduzir incerteza;
- orientar decisões posteriores.

---

# 27. Anti-Patterns

Evitar:

**Research Theater**

Realizar pesquisa apenas para justificar uma decisão já tomada.

**Solution Bias**

Começar pela solução em vez do problema.

**Opinion as Evidence**

Tratar opinião como dado.

**Single-User Generalization**

Generalizar comportamento de uma única pessoa.

**Leading Questions**

Fazer perguntas que induzem respostas.

**Confirmation Bias**

Buscar somente evidências que confirmem a hipótese.

**Vanity Research**

Coletar informações interessantes que não influenciam nenhuma decisão.

**Research Without Decision**

Realizar pesquisa sem definir qual decisão será influenciada pelos resultados.

**False Precision**

Apresentar conclusões com precisão maior do que os dados permitem.

---

# 28. Regra de Ouro

Não pesquisar para provar que uma solução está certa. Pesquisar para entender o problema suficientemente bem para tomar uma decisão melhor.

UX Research deve reduzir incerteza, não produzir documentação por si só.

Quando houver pouca evidência, declarar a incerteza.

Quando houver evidência forte, utilizá-la para orientar decisões.

Quando houver conflito entre evidências, investigar o motivo antes de escolher uma conclusão.
